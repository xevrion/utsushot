# X11 (not planned)

utsushot's whole mechanism depends on something X11 does not have.

On Wayland, each output carries a scale factor, and clients are told what it is.
A GTK or Qt application on a `scale 4` output re-renders its text and vector UI
from source at 4× pixel density. That re-render is the entire product; the
phantom output is just a way to ask for it.

X11 has no per-output scale in that sense. `Xft.dpi` and `GDK_SCALE` are global
and read once at startup, so there is no way to tell a running application to
re-render at a different density for one capture. RandR can add a virtual CRTC
with `--scale`, but that scales the *framebuffer*, which is the raster
interpolation utsushot exists to avoid.

The closest honest X11 equivalent would be restarting the target application
with a higher `GDK_SCALE` inside a nested server such as Xephyr. That is a
different tool with different tradeoffs, not a backend behind the same trait.

XWayland clients under a supported Wayland compositor are a separate matter: they
will be captured at the phantom output's resolution, but since they do not
re-render at the new scale the result is upscaled rather than genuinely sharp.
Expect blurry XWayland windows in an otherwise crisp capture.
